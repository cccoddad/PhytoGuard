# 设计决策记录

> 每条决策按「背景 → 备选方案 → 选择 → 代价」组织，供面试追问时按同一结构回答。

## 1. 两阶段级联推理（而不是单个 16 类模型）

**背景**：原始方案是 1 个 16 类模型（5 作物 × 病害 + healthy + 背景）。

**备选方案**：
- A. 单模型 16 类（原方案）
- B. 两阶段级联：Stage1 判作物（6 类）→ Stage2 按作物判病害（2~4 类）
- C. 6 个模型全部常驻内存

**选择 B**，理由：
1. **样本不均衡**：原始 16 类里各类样本量差异大，背景/healthy 类容易吃掉决策边界；按作物拆开后每个 Stage2 只在 2~4 个类里判别，类别少、类间差异大。
2. **精度**：植物分类 Top-1 98.4%，各病害模型 97.0%~100%（见 training/README.md）。
3. **总参数量不变甚至更小**：6 个 YOLOv8n-cls 共 20.4MB，但每轮只需跑 2 个模型。

**为什么不选 C（全常驻）**：Stage2 有 5 个模型，全常驻的 NPU 内存开销 ≈ 5 × 单模型常驻。板端内存有限，而每帧只会命中其中 1 个。所以实现为**懒加载**：Stage1 出结果后 `aclmdlLoadFromFile` 对应的 OM → 推理 → `aclmdlUnload`（`heshi_v2_dual_infer.c:1673-1715`）。代价是每轮多一次模型加载耗时（毫秒级，需实测确认，见 measurement-notes.md）。

**兼容性处理**：两阶段组合出的 `Plant___Disease` 标签再映射回旧 16 类 ID（`heshi_v2_dual_infer.c:1727-1742`），云端与小程序不用改。

## 2. 预处理只做一次，两阶段共享

**背景**：两个 Stage 输入都是 224×224 NCHW float32。

**选择**：抓帧后只做一次 center-crop → bilinear resize → /255 → HWC→NCHW（`preprocess_rgb_to_nchw`，`heshi_v2_dual_infer.c:941`），产出的 `host_input` buffer 传给两个模型。

**理由**：预处理在 CPU 上做，是推理链路里除 NPU 外最贵的一环；两阶段共享可以把它摊薄一半。

**一致性风险与对策**：训练侧（`training/README.md`）与板端使用同一套预处理口径：短边方形中心裁剪 → resize 224 → 仅 /255（无 ImageNet mean/std）→ NCHW。口径不一致是这类项目精度掉点的头号原因。

## 3. 告警防抖：业务层 + 传输层两道闸

**背景**：单帧误检会刷屏，短信还有成本。

**第一道（业务层，`heshi_v2_dual_infer.c:2056-2089`）**：
- 连续命中 N 次（`DEFAULT_CONSECUTIVE_N`）且置信度 ≥ 阈值才触发告警；
- 类别变化时计数清零重来；healthy 类或低置信度直接清零。

**第二道（传输层，`alert_dispatch.c:522-566`）**：
- HTTP 与 SMS 各自独立节流：同一类别冷却期内不重发（`sms_cooldown_sec`，默认 300s）；类别变化则立即发。
- SMS 成本更高，与 HTTP 分开计时。

**为什么两道**：第一道保证「发出去的告警是真的」，第二道保证「同一件事不重复打扰」。只做其一，要么漏要么刷。

## 4. raw socket 手写 HTTP 客户端（不用 libcurl）

**背景**：板端要把告警 POST 到云端。

**备选**：libcurl vs 手写。

**选择手写**（`alert_dispatch.c:153-302`）：
1. **零依赖**：交叉编译环境不用再打包/裁剪 curl 及其 TLS 依赖；
2. **可控**：收发都设 5 秒超时（`SO_SNDTIMEO`/`SO_RCVTIMEO`），4G 链路抖动时不会永久阻塞推理主循环；
3. **够用**：告警是小 JSON + base64 图，HTTP/1.0 + `Connection: close` 足矣。

**代价**：
- 只支持 `http://`，无 HTTPS（若要上 TLS，需要重新引库或在云端加网络层白名单）；
- 响应解析是「响应里含 200 才算成功」的轻量判断（修复后不会把 401/500 当成功，见 `alert_dispatch.c:292-301`），不是完整 HTTP 解析器。

**同款实现还用在** `status_report.c` 心跳上，两处行为一致。

## 5. 双网口与 4G 链路自愈

**背景**：告警不能依赖单一网络路径。

**设计**：
- 有线 eth0 与 L610 4G ECM 网口并存，路由按系统默认优先级；
- `l610_watchdog.sh` 独立守护进程，每 30 秒四段检测（接口存在 → AT 口可读 → 有 IP → ping 公网），任一失败调 `l610_connect.sh` 重连，连续失败退避到 60 秒；
- `l610_connect.sh` 幂等：已有接口且有 IP 直接退出，可被开机脚本和 watchdog 反复调用。

**与推理进程解耦**：网络守护是独立进程，挂掉不影响推理；推理进程有 `S99heshi` 拉起，单轮失败不退出主循环（`heshi_v2_dual_infer.c:2046-2051`）。

> 注：L610 相关脚本依据常见 ECM 流程编写，**未经实机验证**，AT 指令参数待按模组手册核对（见 board/README.md）。

## 6. 推理进程的降级路径（可用性优先）

板端代码里有一组「尽量不停摆」的降级：
- 图片压缩/编码失败 → 发纯文本告警（`alert_dispatch.c:457-459`）；
- SMS 串口初始化失败 → 只关 SMS，HTTP 继续（`alert_dispatch.c:416-422`）；
- Stage2 模型加载/推理失败 → 退化为只报作物名，或 `Plant___Unknown`（`heshi_v2_dual_infer.c:1702-1711`）；
- SHT3X 打不开 → 无传感器继续跑（`heshi_v2_dual_infer.c:1939-1943`）；
- 单轮推理失败 → 记日志继续下一轮，不退出进程（`heshi_v2_dual_infer.c:2046-2051`）。

**原则**：识别系统里「识别质量下降」可接受，「整个系统停摆」不可接受。
